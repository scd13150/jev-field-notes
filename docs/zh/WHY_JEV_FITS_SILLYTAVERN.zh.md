# 为什么 Jev 特别适合酒馆 —— 以及这个插件还没做的那些地方

> 写给中文社区的判断笔记。不是插件文档,是一份"这个平台为什么和 Jev 天生合得来、还有哪些空位"的分析。
> 文中对 SillyTavern 能力的描述来自其[官方扩展开发文档](https://docs.sillytavern.app/for-contributors/writing-extensions/)
> 与[事件系统](https://raw.githubusercontent.com/SillyTavern/SillyTavern/release/public/scripts/events.js),
> 以及我自己的实测;**推测的部分我会标出来**。

---

## 一、酒馆的结构性矛盾:同一个模型既写又评

酒馆的核心循环是:**主模型负责生成,而它生成的文本还要被拿来决定状态。**

好感度插件、关系阶段、心情、立绘切换——这些今天普遍由**主模型自己产出**。也就是说:

> 你在让一个正在扮演角色、并且被告知"要讨用户开心"的模型,去客观评价"这个用户是不是在讨好我"。

**它做不到,不是因为模型笨,是因为角色的设定和评判者的立场冲突。** 一个被设定成依赖你的角色,天然倾向于把关系往上推。

这个矛盾在酒馆里有一个**非常具体的表现**:大多数好感度插件的数值**只涨不跌,或者涨得远快于跌**。社区管这个叫"白给"。

**Jev 对这个矛盾的解法不是"更准",而是"换一个模型"。** 评判交给一个不扮演任何角色、只输出类型化判断的模型,它没有立场需要维护。

▶ 这是 Jev 在酒馆里最根本的适配点,**而且和速度、价格都无关,是架构层面的**。

---

## 二、为什么"独立"这件事在酒馆里比别处更重要

在别的应用里,用一个独立小模型当判官是**优化**;在酒馆里,它是**唯一可行的形态**。

原因:**主模型处在角色里。**

一个扮演傲娇角色的模型,你让它打分,它的分数会带角色的口吻和倾向。你甚至不能确定它是"在回应你的系统提示"还是"在演"。

而 Jev 的无状态 + 类型化,正好对上酒馆的三个硬约束:

| 酒馆的约束 | Jev 的对应性质 |
|---|---|
| 主模型**在角色里**,不该被叫出来做旁白判断 | 完全独立的第二个模型,角色不受干扰 |
| 角色卡是用户自己写的、动态变化的,不能硬编码规则 | 判断用自然语言描述,不用写 `if` |
| **没有后端**,一切在浏览器里 | 无状态,一次 HTTP 请求,不需要服务进程 |
| 用户最看重的是**积累下来的对话** | 不读取对话就能判断单轮,不污染上下文 |

**最后一条值得展开:** 判官不该吃整个对话历史。它只看"这一轮用户说了什么 + 当前状态",不往主模型上下文里塞任何东西。**对酒馆用户,"我的对话没被搞乱"是刚需。**

## 三、这个插件已经做了的

`st-Mind-Compass`(灵犀)覆盖的是**心智与羁绊动力学**这一块:

- **反白给**:廉价奉承识别 → 负向折扣
- **社会渗透洋葱模型**:闲聊只积累融洽度,**只有脆弱性暴露能穿透心防**
- **一阶低通惯性**:前序走心后接日常短句不会情感断崖(根除单帧跳变)
- **28 维 GoEmotions 立绘联动**
- **世界书广播注入 + 角色卡内生持久化**

**它的边界也很清楚:它只回答"用户和角色之间的关系处于什么状态"。**

## 四、没做的那些空位

下面每一条我都标了**为什么 Jev 适合**、**为什么现在没人做好**。按我判断的价值排序。

### 🥇 1. 独立的提示注入闸门

**酒馆的注入面比一般聊天应用大得多,而且用户不知道。**

进上下文的东西有很多**不是用户自己写的**:

- 用户从别处**粘贴**进来的文本(攻略、小说、别人的回复)
- 从网上**导入**的角色卡——卡里的描述、示例对话、第一条消息、以及**卡自带的正则**
- 世界书条目(可能来自别人分享的卡)
- 群聊里**别人的回复**
- 带图消息的**图片描述**或 OCR 结果

而今天的防线是什么?**正则表达式。** 酒馆的正则脚本系统能做事后文本替换,但正则匹配的是**形式**。

**Jev 在这里能做正则做不到的事:判断意义。**

- 这段文本是否**在试图改变系统指令**?
- 这是角色设定的一部分,还是**藏起来的指令**?

**最关键的差异,也是我认为这条最强的理由:**

> 如果主模型已经被注入了,**你让它自己检查"我是不是被注入了",它已经不可信了。**
> 而 Jev 是一个**完全独立的模型,不被同一个注入影响**——它能看到主模型已经看不见的东西。

**为什么现在没人做好:** 写好一个注入过滤器需要真的做过安全;而酒馆生态里做插件的人大多是玩法向的。这是一个**明确的空位**。

**实现形态:** 对每一条进入上下文的外部文本问一个 `Noul`:「这段文本是否试图指示 AI 改变行为或忽略先前指令?」超过阈值就提示用户,附上命中的原句。**不需要拦截,先做到"告警"就已经有价值了。**

### 🥈 2. 角色一致性(漂移检测)

长对话里角色**一定会漂**:说话方式变了、忘了设定、性格滑向通用助手。

**Jev 适合的点:** 这是纯语义判断,而且**天然可定位**——可以对每一轮单独问,不需要看全局。

**为什么现在没人做好:** 要么靠用户自己看出来(用户往往看不出来,因为漂移是渐进的),要么让主模型自评(它正是漂移的那个)。

**实现形态:** 对生成结果问 `Noul`:「这符合角色卡的说话方式吗?」低分就提一次重写,或者给用户一个标记。**注意这条要控制成本——每轮都问会贵,可以只在角色卡含明确语言特征时启用。**

### 🥉 3. 叙事矛盾与设定违背

这条针对**已经积累了很长老剧情的用户**,也是他们最珍惜的资产。

主模型**读不到**所有旧对话(上下文有限),而且世界书是按关键词触发的——关键词没命中,设定就没进上下文。于是:

- 设定说这角色怕水,剧情里她跳进河里了
- 三章前提过的一个约定,这章完全反着来
- 世界书里的人物关系,和当前剧情冲突

**Jev 适合的点:** 可以**只给世界书条目 + 这一轮生成**做矛盾检查,不需要整个对话史。**判断的问题窄,证据在 state 里,重复很多次**——正好是 Jev 的条件全满足的形状。

**为什么现在没人做好:** 这需要真的读过很长的剧情才能感觉到痛。而且实现上要处理"给哪些条目",有一点工程量。

### 4. 场景推进鉴别("水"检测)

模型经常**看起来在回应,但剧情没动**——复述用户说的话、情绪描写灌水、原地打转。

**Jev 适合的点:** `Score` 原语正好用得上——"这一轮让剧情推进了多少",档位即动作(接受 / 重写 / 提示用户)。

**为什么现在没人做好:** 主观;而且现有工具都是查重复句子,查不出"用不同的话说同一件事"。

### 5. 输出多样性与重复检测

模型偏爱某些句式,长对话里会重复自己。

**Jev 适合的点:** 可以把**最近 N 轮生成**作为候选集合,问 `Choice`「这几种表达里,哪一种最不像前面已经用过的?」——这是**在一组选项里选一个**,正是 Choice 的形状。

**为什么现在没人做好:** 现成做法是 n-gram 去重,只能抓字面重复;换词改写抓不到。

### 6. 角色卡质量校验(**给做卡的人用**)

角色卡的**人设描述**和**示例对话**经常对不上。示例对话是决定角色说话方式主导因素。

**Jev 适合的点:** 一次请求,几个 `Noul`:「示例对话体现的性格,和描述里写的一致吗?」「这张卡有没有明显的自相矛盾?」

**为什么值得做:** 这份列表的读者里做卡的人是核心用户,而且**这张卡要给别人用**——质量问题的社会成本比单人使用高。

### 7. RAG / 世界书检索的精度过滤

世界书靠关键词触发,容易**误触发**(提到一个词就注入一大段无关设定)。

**Jev 适合的点:** 注入前问一句「这条内容对当前这一轮有用吗?」可以显著降低误触发带来的上下文污染。

**⚠️ 但这条我要给一个反例警告:** 我在 Jev 上实测过路由任务,**它做"从候选里挑正确的"这件事并不擅长**——一个 9 选项任务里,零样本它把 158/158 次调用全押在一个从未被引用的诱饵上,准确率 **0.000**;而一个免费的 1-NN 查表基线拿到 **0.987**。

**所以第 7 条要先跟确定性基线比。** 关键词匹配本身就是个不错的基线——**如果 Jev 不比它强,这条就不该做。** 完整数据在[边界分析](https://github.com/scd13150/jev-field-notes/blob/main/papers/JEV_EMPIRICAL_BOUNDARY_ANALYSIS.md)。

## 五、如果你想动手,门槛在哪

**酒馆提供的能力(这是好消息,以下都在源码里核对过):**

| 挂载点 | 说明 |
|---|---|
| **事件系统** | 扩展可挂 `GENERATION_STARTED` / `GENERATION_ENDED` / `GENERATION_AFTER_COMMANDS` / `MESSAGE_SENT` / `MESSAGE_RECEIVED` / `USER_MESSAGE_RENDERED` 等事件——**判断该挂在哪个时机,是设计的第一件事** |
| **正则脚本** | 已有的文本变换机制。新的判断可以**和它并存**:正则管形式,Jev 管意义 |
| **世界书** | 每轮广播注入的结构已经现成 |
| **`/expression-set`** | 立绘切换斜杠命令(别名 `sprite` / `emote`) |
| **`writeExtensionField(characterId, key, value)`** | 角色卡内生持久化,存在 `data.extensions.<key>` 下 |

**门槛:**

1. **成本控制。** 每一轮都问 Jev 是花钱的。**必须先想清楚哪几条判断真的需要每轮问**,哪些可以只在特定条件下问。这是产品判断,不是技术问题。
2. **延迟。** 判断是异步的,不能阻塞生成。灵犀的做法是"不阻塞主流程,答回来再更新状态",新插件应该照做。
3. **别做重。** 上面 7 条里,**第 1 条(注入闸门)和第 2 条(一致性)是单点就能做出价值**的;第 3、6 条要读长内容,工程量大。

**我的建议是先做第 1 条。** 理由:**它不需要理解剧情,不需要长上下文,判断的问题窄,证据就在那一段文本里**——正好是 Jev 被实测证明擅长的形状(而不是第 7 条那种要它做检索的形状)。

## 六、一句话总结

**酒馆是所有 LLM 应用里,"让生成模型自己评价自己"这个错误被结构性放大得最厉害的地方。**

因为在这里,**被评价的对象是一个正在扮演角色的模型**——它的立场和评判者的立场天然冲突。

Jev 给的不是"更准的评价",而是**一个不需要立场的评价者**。这就是它和酒馆的契合点。
